# Releasing

This project uses [Semantic Versioning](https://semver.org/) and GitHub Releases with prebuilt binaries.

There are two supported ways to cut a release:

1. **Automatic** via [semantic-release](https://semantic-release.org/) when Conventional Commits land on `main`
2. **Manual** by bumping `Cargo.toml`, updating `CHANGELOG.md`, and pushing an annotated `vX.Y.Z` tag

Both paths end in the same place: tag `vX.Y.Z` triggers (or is handed to) [`.github/workflows/release.yml`](.github/workflows/release.yml), which builds binaries and attaches them to the GitHub Release.

## Version sources

| Location | Purpose |
| --- | --- |
| `Cargo.toml` `version` | Canonical crate / CLI version |
| `CHANGELOG.md` | Human-readable release notes |
| Git tag `vX.Y.Z` | Identifies the release and starts binary publishing |

The CLI reports `CARGO_PKG_VERSION` and a short git commit via `--version`.

## Automatic releases (semantic-release)

[semantic-release](https://semantic-release.org/) runs after **CI** succeeds on `main` ([`.github/workflows/semantic-release.yml`](.github/workflows/semantic-release.yml)). You can also start it by hand with **Actions → Semantic Release → Run workflow**.

It:

1. Reads commits since the last `vX.Y.Z` tag
2. Decides whether a release is needed and which SemVer bump to apply
3. Updates `CHANGELOG.md`, `Cargo.toml`, `Cargo.lock`, and README download URLs
4. Commits `chore(release): X.Y.Z [skip ci]`, creates tag `vX.Y.Z`, and opens a GitHub Release
5. Calls the binary **Release** workflow so archives are attached to that tag

`GITHUB_TOKEN` cannot start new workflows from the tag it pushes, so binary publishing is invoked with `workflow_call` rather than relying on the tag `push` event.

### Conventional Commits

Write commit messages (or PR titles, if you squash) using [Conventional Commits](https://www.conventionalcommits.org/):

| Prefix | Release | Changelog section |
| --- | --- | --- |
| `feat:` | minor (`0.2.0` → `0.3.0`) | Added |
| `fix:` | patch | Fixed |
| `perf:`, `refactor:`, `revert:` | patch | Changed / Fixed |
| `feat!:` or `BREAKING CHANGE:` footer | major (`0.2.0` → `1.0.0`) | Breaking change notes |
| `docs:`, `chore:`, `test:`, `ci:`, `style:` | none | omitted |

Examples:

```text
feat: add PDF page-size option
fix: reject due dates before the invoice date
feat!: require invoice.currency
```

If nothing since the last tag matches a releasing type, semantic-release exits without publishing.

### Dry run

Requires Node.js 20.8+ (release tooling only; the CLI itself is Rust):

```bash
npm ci
GH_TOKEN="$(gh auth token)" npx --no-install semantic-release --dry-run
```

This prints the next version and notes without tagging or pushing.

### On-demand automatic release

Use **workflow_dispatch** on the Semantic Release workflow when CI already passed but you want to retry publishing, or when you merged releasing commits and want to run it without waiting for `workflow_run`.

## Manual releases

Use this when you need a version that commit messages would not produce, or when you are not using Conventional Commits for a change.

1. **Update `CHANGELOG.md`**
   - Move items from `[Unreleased]` into a new `## [X.Y.Z] - YYYY-MM-DD` section (or `## [X.Y.Z](...)` as generated by semantic-release).

2. **Bump the crate version**
   ```bash
   python3 scripts/prepare-release.py X.Y.Z Y.Y.Y
   ```
   `Y.Y.Y` is the previous release. This updates `Cargo.toml`, `Cargo.lock`, README install URLs, and changelog compare links.

3. **Commit on `main`**
   ```bash
   git checkout main
   git pull
   git add CHANGELOG.md Cargo.toml Cargo.lock README.md
   git commit -m "Release vX.Y.Z"
   ```

4. **Tag and push**
   ```bash
   git tag -a vX.Y.Z -m "Release vX.Y.Z"
   git push origin main
   git push origin vX.Y.Z
   ```

   Optional local check before pushing the tag:

   ```bash
   ./scripts/verify-release.sh vX.Y.Z
   ```

5. **Verify the GitHub Release**
   - The tag push runs [`.github/workflows/release.yml`](.github/workflows/release.yml), which checks that the tag matches `Cargo.toml`, extracts the changelog section, builds binaries, and publishes or updates the GitHub Release.

Do not push a manual tag for a version semantic-release is about to create from the same commits; pick one path per release.

## Tag rules

- Tags must match `vMAJOR.MINOR.PATCH` (for example `v0.2.0`).
- The tag without `v` must exactly match `Cargo.toml` `version`.
- A matching `## [X.Y.Z]` or `# [X.Y.Z]` heading must exist in `CHANGELOG.md`.

## Release artifacts

Each release publishes archives for:

- `x86_64-unknown-linux-gnu`
- `aarch64-unknown-linux-gnu`
- `aarch64-apple-darwin`
- `x86_64-apple-darwin`
- `x86_64-pc-windows-msvc`

Archive names follow:

```text
invoicemd-cli-<version>-<target>.tar.gz
invoicemd-cli-<version>-<target>.zip   # Windows
```

Each archive includes the binary, `README.md`, `CHANGELOG.md`, `templates/default.html`, and `examples/*.yaml`.

## Local verification before tagging

```bash
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --check
cargo build --release
./target/release/invoicemd-cli --version
```

## Installing from a release

Download the archive for your platform from GitHub Releases, extract it, and run `invoicemd-cli` from the extracted directory (or move the binary onto your `PATH`).

## Protected `main`

Automatic releases commit back to `main` with `GITHUB_TOKEN`. If the branch is protected, allow GitHub Actions to push (or use a fine-grained PAT / GitHub App token as `GITHUB_TOKEN` in the Semantic Release job). Manual tagging with your own credentials is unaffected.
